## Session tooling notes (things that cost time to learn — don't relearn them)

- **Inline tool-result images are NOT visible to the user in this environment.** Only `SendUserFile` actually reaches them. If asked to "show me the image," use `SendUserFile`, not just a Read-tool image display.
- **Large images can fail `SendUserFile` uploads silently (server 400) with no size threshold given.** An 8566px-wide/4MB panorama failed twice; resizing to ~2400px wide via PowerShell + `System.Drawing` (see git log for the snippet) fixed it. Keep hero/background images around 2400px wide, ~80% JPEG quality as a safe default — good enough for web display, small enough to upload reliably.
- **Turbopack dev-server HMR can go stale after large-scale file restructuring.** After moving/deleting many files across modules in one session, `next dev` rendered every background image as solid black despite the network requests succeeding (200). `npm run build` was correct the whole time. A full `taskkill /IM node.exe /F` + fresh `npm run dev` fixed it immediately. If a screenshot ever looks wrong in a way the code doesn't explain, restart the dev server before assuming the code is broken.
- When downloading images from Wikimedia Commons via `curl`, always check the actual bytes downloaded (`head -c 300 file.jpg`) before trusting the file — at least one download silently returned an HTML "Wikimedia Error" page instead of the image (fixed by retrying with a browser-like User-Agent header).
- **This machine's network cannot reach Postgres ports (5432/6543) outbound at all** — confirmed via raw TCP tests (`/dev/tcp` in bash, and a .NET `TcpClient` in PowerShell) to both Supabase's direct-connection host and its pooler host, with `dangerouslyDisableSandbox: true` on both tools to rule out a Claude-Code-specific restriction. HTTPS (443) works fine, so it's specifically those ports being blocked — most likely the router/ISP. A mobile-hotspot fallback also failed, but for a *different* reason (the hotspot had an IPv4 address with no IPv4 default gateway — only an IPv6 one — so IPv4-literal connections like Postgres had nowhere to route). **Practical upshot: any future local `npx prisma migrate dev/deploy` or direct DB connection from this machine will likely fail the same way.** Use the GitHub Actions workflow (`.github/workflows/db-migrate.yml`, `workflow_dispatch` only) instead — it runs on GitHub's infrastructure, which has no such restriction.
- **To add a new migration going forward** (schema.prisma changes): generate the diff locally without needing a live DB connection — `npx prisma migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma --script -o prisma/migrations/<timestamp>_<name>/migration.sql` (check exact flag names against the installed Prisma version first; they changed between versions this session — `--to-schema-datamodel` became `--to-schema`). Commit it, then trigger `db-migrate.yml` to apply it via `migrate deploy`. Don't try `migrate dev` locally — it needs a live connection this machine doesn't have.
- **Writing to a remote secret store (e.g. `gh secret set`) is blocked by an auto-mode safety guardrail**, even when the values are already known/local (e.g. already in `.env`). Create the resource (workflow file, etc.) and ask the user to paste the secret values into the GitHub web UI themselves (Settings → Secrets and variables → Actions) — don't try to work around the block.
- `gh` CLI needed a one-time interactive device-code auth (`gh auth login --web` prints a URL + code; user opens it and approves in their own browser while the command polls in the background) — already done for this session/machine, no need to repeat.
